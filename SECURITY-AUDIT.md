# CAT FTX-1 — Security Audit Report

- Project: `cat-ftx1` v1.0.1 (Yaesu FTX-1 CAT Controller)
- Audit date: 2026-05-26
- Auditor: automated source review + `npm audit`
- Scope: source tree under `cat-ftx1-main/` (Nuxt 3 app, Electron shell, standalone `serial-server.mjs`) and `package-lock.json` (transitive dependencies)
- Out of scope: the FTX-1 firmware itself, OS-level serial-port permissions, code-signing / installer integrity

---

## 1. Executive summary

| Area | Findings | Highest severity |
|---|---|---|
| Local HTTP API (`serial-server.mjs`) | 8 | High |
| Nuxt server / proxy layer | 3 | High |
| Electron shell | 3 | Medium |
| Frontend (Vue / Nuxt) | 2 | Low |
| Dependencies (`npm audit`) | 21 (2 low, 7 moderate, 12 high) | High |
| Logging / file I/O | 2 | Low |
| Supply chain / build | 2 | Medium |

The single most consequential finding is **APP-01**: the Nuxt API (which proxies the full set of CAT commands) is started by the Electron main process via `utilityProcess.fork(... { env: { PORT: '3000' } })`. Nitro's Node preset defaults to binding on **all network interfaces** when `HOST` is unset. Combined with **no authentication, no origin check, and no CSRF protection** on `/api/command`, `/api/connect`, `/api/preset-execute`, this means **any device on the same LAN — or any web page the operator visits while the app is running — can put the radio into TX, change frequency / mode, or disconnect it.** Because the FTX-1 is a transmitter, that has real-world regulatory/safety implications, not just an IT one.

Everything else is conventional web/Electron hygiene plus 21 known-vulnerable transitive dependencies.

No remote code-execution path was found in the project's own source. The serial server's command channel is data only (forwarded as bytes to the radio), so the worst-case impact via the network paths is "unauthorized radio control + denial of service against the serial-server process".

---

## 2. Threat model (assumed)

- T1: A malicious or compromised web page opened in any browser on the operator's machine while CAT FTX-1 is running.
- T2: Another host on the same Wi-Fi / LAN segment as the operator (home network, hamfest, club station).
- T3: A local non-privileged user account on a shared computer.
- T4: A supply-chain compromise of a transitive npm dependency at install / rebuild time.
- T5: A malicious USB-serial device pretending to be an FTX-1.

The app explicitly trusts the local machine (no auth, no encryption), which is reasonable for a single-user desktop tool — but only if the listener stays loopback-bound and CSRF/DNS-rebinding are addressed.

## 3. Findings — application code

### APP-01 — Nuxt API server binds to all interfaces, no auth, no CSRF protection  **[HIGH]**

- Files:
  - `electron/main.mjs` lines 40–51
  - `server/api/command.post.ts`, `connect.post.ts`, `disconnect.post.ts`, `preset-execute.post.ts`, `ports.get.ts`, `status.get.ts`, `presets.get.ts`
- Description: The Electron main process starts the built Nitro server with only `PORT: '3000'`; it does not set `HOST` or `NITRO_HOST`. Nitro's default behavior is to listen on `0.0.0.0`, so the Nuxt API is reachable from any host that can route to the operator's machine. The endpoints have no authentication, no origin / referer check, no CSRF token, and accept `application/json` (which lets a malicious page issue requests via `fetch` with `mode: 'cors'` — even if CORS blocks the response, the side-effect on the radio has already happened, since `/api/command` is a "simple" POST mutator that returns success).
- Impact:
  - Any LAN attacker can issue `POST /api/connect` + `POST /api/command { "command": "TX1" }` and key the transmitter, change frequency, disable lock, etc.
  - Any web page the operator browses can do the same via CSRF (`fetch('http://localhost:3000/api/command', { method: 'POST', body: ... })`).
- Reproduction:
  1. Start the Electron build on machine A.
  2. From machine B on the same network: `curl -X POST http://A:3000/api/command -H 'Content-Type: application/json' -d '{"command":"TX1"}'`.
- Recommendation:
  - In `electron/main.mjs`, set `HOST: '127.0.0.1'` (or `NITRO_HOST: '127.0.0.1'`) in the env passed to the forked Nitro process.
  - In every `server/api/*.ts` handler, require either:
    - a `Host` header matching `127.0.0.1:3000` / `localhost:3000`, and an `Origin` header that is `null`, `http://localhost:3000`, or `http://127.0.0.1:3000` (block DNS-rebinding hostnames and remote origins), **or**
    - a per-launch shared secret token (random, generated by the Electron main process at startup, written into the renderer via `runtimeConfig` and required as a header on every API call).
  - For dev (`npm run dev` / Nuxt dev server), keep the same loopback bind: configure `nitro.devServer.host = '127.0.0.1'` in `nuxt.config.ts`.

### APP-02 — `serial-server.mjs` CORS `Access-Control-Allow-Origin: *` on a privileged local service  **[HIGH]**

- File: `serial-server.mjs` lines 632–638, 757.
- Description: The standalone serial server listens on `127.0.0.1:3001` (good), but every response carries `Access-Control-Allow-Origin: *` and `Access-Control-Allow-Methods: GET, POST, OPTIONS`. That makes the `/events`, `/status`, `/ports`, `/connect`, `/disconnect`, `/command`, `/preset` endpoints reachable from any web page the user visits (CSRF + read-side via fetch / `EventSource`). The Host header is not validated, so DNS-rebinding attacks against `127.0.0.1:3001` are also possible.
- Impact: Same as APP-01, but more direct: the page can target the serial server even when the Electron app isn't running, as long as the user started it as a Node service.
- Reproduction:
  ```js
  await fetch('http://127.0.0.1:3001/connect', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ port: 'COM3', baudRate: 38400 }),
  })
  await fetch('http://127.0.0.1:3001/command', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ command: 'TX1' }),
  })
  ```
- Recommendation:
  - Remove the wildcard CORS header. The only legitimate client is the Nuxt server-side handlers in `server/api/*.ts`, which are server-to-server and never need CORS at all.
  - Validate `req.headers.host === '127.0.0.1:3001'` (reject `localhost`, `*.localtest.me`, attacker-controlled DNS names that resolve to `127.0.0.1`).
  - Validate `req.headers.origin`: either absent (server-to-server) or matching the expected localhost origin.
  - Require a per-launch token (shared with the Nuxt process via the env var Electron already plumbs through).

### APP-03 — No allow-list / validation on CAT command strings  **[HIGH]**

- Files: `serial-server.mjs` lines 696–721 (`/command`) and 723–749 (`/preset`); `server/api/command.post.ts`; `server/api/preset-execute.post.ts`.
- Description: `body.command` is passed through with only `.replace(/;+$/, '').trim()` and written verbatim to the serial port. There is no length limit, no character allow-list, no rate limiting, and no per-command authorization (e.g., "TX commands require a confirm"). Combined with APP-01/APP-02 this is what makes unauthorized transmission possible.
- Impact: Bricking-style misuse is unlikely (the FTX-1 ignores unknown CAT frames), but **TX**, **PS0 (power off)**, lock toggles, frequency / mode / power changes are all unrestricted. Long payloads will also flood the serial buffer.
- Recommendation:
  - Add a server-side allow-list of CAT command prefixes the UI actually uses (the set in `serial-server.mjs` `_parseResponse` and in `pages/index.vue` is finite — ~50 prefixes).
  - Reject commands longer than e.g. 32 bytes.
  - Optional but valuable: require an explicit "transmit acknowledged" flag in the request body for any command that can key the PTT (`TX`, `MX`, `MOX`, `FT`).
  - Reject `body.command` that is not a plain ASCII string of `[A-Z0-9+\-]`.

### APP-04 — Unauthenticated SSE stream leaks live operator state  **[MEDIUM]**

- File: `serial-server.mjs` lines 659–680.
- Description: `GET /events` streams the full transceiver state (frequencies the operator is on, modes, S-meter readings, TX state, firmware versions, ANT selection, lock state) to anyone who can reach the server. Because of APP-02 the CORS policy lets any web page open an `EventSource` against it.
- Impact: Operational privacy disclosure (which bands/freqs the operator monitors, when they transmit). Also a covert channel: a malicious page can fingerprint that the user has an FTX-1 + SPA-1.
- Recommendation: same fixes as APP-02 (loopback host check, no wildcard CORS, token).

### APP-05 — Unbounded request body parser  **[MEDIUM]**

- File: `serial-server.mjs` lines 611–621 (`readBody`).
- Description: `readBody` does `data += chunk` with no size limit and no timeout. A LAN attacker (see APP-02) can send a multi-gigabyte POST and exhaust memory in the serial-server process.
- Impact: DoS of the serial server (and thus the radio control), one POST per attempt.
- Recommendation: Cap `data.length` at e.g. 4 KB; destroy the socket and respond 413 if exceeded. Add an `req.setTimeout(5000)`.

### APP-06 — Arbitrary serial-port path passed to `SerialPort`  **[MEDIUM]**

- File: `serial-server.mjs` lines 110–117, plus `/connect` handler line 683.
- Description: `body.port` is forwarded straight into `new SerialPort({ path: portPath, ... })`. There is no validation that the path is in the list returned by `SerialPort.list()`. On Windows that's mostly limited to `COM*` device names, but on Linux/macOS the value can be any character-device path the process can open (e.g. `/dev/tty*`, `/dev/urandom`, etc.).
- Impact: A network attacker (per APP-01/02) can force the app to open or hold unrelated devices, potentially interfering with other applications. Not a privilege-escalation, but unexpected I/O.
- Recommendation: After calling `SerialPort.list()` once, only accept `port` values that exactly match a `path` from that list.

### APP-07 — Per-launch error messages echoed back to client  **[LOW]**

- Files: `server/api/command.post.ts`, `connect.post.ts`, `disconnect.post.ts`, `preset-execute.post.ts`, `ports.get.ts`, `status.get.ts`; `serial-server.mjs` `send(res, 500, { error: err.message })` line 753.
- Description: Upstream `err.message` is echoed verbatim. For local-only use this is fine, but combined with the LAN exposure above it discloses OS-level error text (`EACCES`, full Windows device paths, etc.) to remote attackers.
- Recommendation: Once authentication is in place, errors can be returned as today. Without auth, log internally and return a generic `{ error: 'serial command failed' }`.

### APP-08 — No process-level rate limiting on serial writes  **[LOW]**

- File: `serial-server.mjs` `/command` and `/preset`.
- Description: The serial queue is internal and bounded by command throughput, but there is no rate limit on inbound HTTP requests. An attacker can saturate the queue and stall legitimate UI commands.
- Recommendation: simple in-memory rate limit (e.g. 20 req/sec per remote IP) on `/command` and `/preset`.

## 4. Findings — Nuxt server (`server/api/*.ts`)

### NUXT-01 — No input schema validation  **[MEDIUM]**

- Files: all `server/api/*.post.ts`.
- Description: Handlers do `readBody(event)` and forward `body` to the serial server with no schema check (apart from `presence` of `command`/`commands`). Types like `port`, `baudRate`, `command` are not coerced or validated.
- Impact: Garbage / hostile payloads reach the serial server; combined with APP-05 this is the easiest DoS path.
- Recommendation: Add a tiny validator (Zod, valibot, or hand-rolled). Reject early.

### NUXT-02 — No CSRF token, no SameSite, no Origin check  **[HIGH]** (covered by APP-01 remediation)

- Same files; mentioned separately because the fix lives in Nuxt, not the serial server.
- Recommendation: When you add the per-launch token described in APP-01, attach it via the Nuxt runtimeConfig (server-only, not `public.`) and require it as a header on each `server/api/*` route via a Nitro middleware in `server/middleware/auth.ts`.

### NUXT-03 — `presets.get.ts` path source is environment-controlled  **[INFO]**

- File: `server/api/presets.get.ts` lines 18–22.
- Description: `process.env.CAT_RESOURCES_PATH` is set by the trusted Electron main process. Not a vulnerability today, but if that env var is ever overridable from outside, `resolve(env, 'cat-presets.json')` would allow opening any file the Node process can read.
- Recommendation: Keep as-is, but document that `CAT_RESOURCES_PATH` must come from Electron only. Optionally `path.normalize` and ensure the result ends with `cat-presets.json`.

## 5. Findings — Electron shell

### EL-01 — `BrowserWindow` created without explicit `webPreferences` / CSP  **[MEDIUM]**

- File: `electron/main.mjs` lines 54–60.
- Description: `new BrowserWindow({ width: 1400, height: 900 })` relies on Electron 41 defaults (which are safe: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`). However:
  - No explicit `webPreferences` block makes future regressions easier.
  - No `Content-Security-Policy` header / meta tag on the rendered Nuxt page. Any future XSS in `pages/index.vue` would have full ability to call back-end APIs.
  - No `webContents.setWindowOpenHandler` / `will-navigate` handler — a stray `<a target="_blank">` could open arbitrary URLs in a new Electron window.
- Recommendation:
  ```js
  win = new BrowserWindow({
    width: 1400, height: 900,
    webPreferences: {
      contextIsolation: true,
      nodeIntegration: false,
      sandbox: true,
      webSecurity: true,
    },
  })
  win.webContents.setWindowOpenHandler(({ url }) => {
    // Block all child windows; if you ever need external links, route via shell.openExternal
    return { action: 'deny' }
  })
  win.webContents.on('will-navigate', (e, url) => {
    if (!url.startsWith('http://localhost:3000')) e.preventDefault()
  })
  ```
  And add a `Content-Security-Policy` meta tag in `app.vue` (or a Nitro response header) restricting `default-src 'self'`, `connect-src 'self' http://127.0.0.1:3001`, `style-src 'self' 'unsafe-inline'` (for Vue's scoped styles), etc.

### EL-02 — `loadURL('http://localhost:3000')` with a 1500 ms race window  **[LOW]**

- File: `electron/main.mjs` lines 54–60.
- Description: A fixed `setTimeout(..., 1500)` is used to wait for the Nitro server. If startup is slow the renderer races and shows a connection-refused page; if startup is fast enough that another process bound port 3000 first, the Electron window will load *that* process. Local but non-privileged user T3 can pre-bind port 3000.
- Recommendation: Poll `http://127.0.0.1:3000/api/status` until it responds 200, then `loadURL`. Or, on each launch, pick a random free port and pass it to both Nitro and `loadURL`. Combine with EL-01's `will-navigate` filter and APP-01's loopback bind.

### EL-03 — Log file path is hard-coded to the user's Desktop  **[LOW]**

- Files: `electron/main.mjs` line 9 (`os.homedir()/Desktop/serial-server.log`), `electron/serial-wrapper.mjs` lines 4–10.
- Description: Logs are written to the user's Desktop with no consent and no rotation. On Windows / macOS where the Desktop is sometimes synced (OneDrive / iCloud), this may upload stack traces, OS paths, COM port names, and firmware versions to a cloud provider.
- Recommendation: Use `app.getPath('logs')` (Electron) or `app.getPath('userData')`. Cap file size, rotate, and gate behind an opt-in setting.

## 6. Findings — Frontend (`pages/index.vue`, `components/`)

### FE-01 — `localStorage` items parsed without schema check  **[LOW]**

- File: `pages/index.vue` lines 784–791.
- Description: `JSON.parse(localStorage.getItem('cat_channels'))` is wrapped in try/catch so it cannot crash the app, but the parsed result is assigned to `savedChannels.value` and later rendered. Because the values are never written to `v-html`, this is informational only. If a future change ever renders saved-channel labels via `v-html`, that would become a stored XSS sink.
- Recommendation: Validate that the parsed value is an array of objects with the expected primitive fields; drop anything unexpected. Keep the `v-text` / mustache rendering it currently has.

### FE-02 — No CSP / Trusted Types  **[LOW]**

- Covered by EL-01.

Almost all of these are **devDependency**-only (they live in `electron-builder` / `@electron/rebuild` and are only used at build time, not in the shipped binary). The Nuxt / Nitro / postcss / devalue / ws ones do ship in the runtime `.output/`. None are critical for this app's threat model on its own, but they should be upgraded.

### DEP-01 — Update vulnerable dependencies  **[HIGH]**

- Recommendation:
  - `npm audit fix` will resolve everything that is a non-breaking bump.
  - For `@electron/rebuild`: pin to `^4.0.4` (major bump; verify `electron:rebuild` and `electron:build` still work — both scripts call `electron-rebuild -f -w serialport` which is unaffected by the API change in v4).
  - For Nuxt / Nitro: bump `nuxt` to the latest 3.x patch (or 4.x — note: Nuxt 4 has minor template breakages; `pages/index.vue` uses only Composition API + `$fetch`, so the migration is small but should still be done in a separate change).
  - For `electron-builder`: bump `^24.13.3` → `^26.x` to pull in fixed `app-builder-lib` and `xmldom`.
- See SC-01 for verification process.

## 8. Findings — supply chain / build hygiene

### SC-01 — `npm install` runs `postinstall` (`nuxt prepare`) — fine, but no integrity guard  **[INFO]**

- File: `package.json` line 14.
- Description: Standard Nuxt setup. Risk is limited because no obviously suspect dependencies are pulled in. Just flagging that `postinstall` scripts run with the user's privileges and can be abused if a transitive dep is compromised.
- Recommendation: Consider `npm ci --ignore-scripts` in CI / one-off audits; use `npm config set ignore-scripts true` on machines that only audit.

### SC-02 — Unused dependency: `shell-quote`  **[LOW]**

- File: `package.json` line 25.
- Description: `shell-quote` is listed in `dependencies` but `Grep` shows it is not imported anywhere in `cat-ftx1-main/`. Dead dependencies inflate the install footprint and create future risk if the package becomes vulnerable or hijacked.
- Recommendation: Remove from `dependencies`. (Note: it is also a transitive dependency of several devDeps; the lockfile will keep that entry, which is fine.)

### SC-03 — No `.npmrc` `engine-strict`, no `npm-shrinkwrap.json` for production  **[INFO]**

- Description: The shipped Electron binary bundles `.output/` and a subset of `node_modules/`. `electron-builder.yml` does not specify an `asarUnpack` rule or `node_modules` filter, which is fine, but in combination with the dependency findings it means **any future `npm install` could pull in newly-vulnerable transitive packages without anyone noticing**.
- Recommendation: Pin Node version (`engines.node`) and add a CI step that fails on `npm audit --audit-level=high`.

## 9. Prioritized remediation plan

P0 — must fix before any further public release:

1. **APP-01 / NUXT-02** — bind Nitro to `127.0.0.1`; add per-launch token + Nitro auth middleware; or at minimum verify Host + Origin headers.
2. **APP-02** — remove `Access-Control-Allow-Origin: *` from `serial-server.mjs`; verify Host header; do not expose `/events`, `/command`, `/preset` to browsers.
3. **APP-03** — allow-list of CAT command prefixes server-side.
4. **DEP-01** — `npm audit fix` (non-breaking) + plan a major bump of `@electron/rebuild` and `electron-builder`.

P1 — fix soon:

5. **APP-05** — body-size cap.
6. **APP-06** — validate `body.port` against `SerialPort.list()`.
7. **EL-01** — explicit `webPreferences`, `setWindowOpenHandler`, `will-navigate`, and a CSP meta tag.
8. **NUXT-01** — schema-validate request bodies.

P2 — nice to have:

9. **APP-04, APP-07, APP-08** — token-gate SSE, generic error responses, simple rate-limit.
10. **EL-02, EL-03** — port-readiness polling and logs under `app.getPath('logs')`.
11. **SC-02** — drop unused `shell-quote` dep.
12. **FE-01** — schema-validate `localStorage.cat_channels`.

## 10. Notes on what was checked and not found

- No `eval`, `new Function`, `child_process.exec`, `vm.runInThisContext`, or `v-html` in the project's own source.
- No use of `nodeIntegration: true` or `contextIsolation: false`.
- No hardcoded credentials, tokens, or secrets in source.
- No SQL / shell-command construction (the project has no database).
- No use of `unsafe-eval` style template features.
- Frontend renders text via mustache / `v-text` only; no XSS sinks were observed in `pages/index.vue` or `components/`.
- The serial-server's response parser uses `parseInt` / explicit substrings and is robust against malformed CAT frames (threat T5 produces at most `NaN` / `null` state values, not crashes).
- Electron 41 is current; the project tracks an up-to-date major.
